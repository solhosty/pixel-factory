# 3H — Demo rehearsal and cinematic polish

Prerequisite: 3G. This packet prepares the real product for a high-confidence recorded demonstration. It is not a video-production script written in advance: the strongest story must be discovered by exercising the product, correcting visible weaknesses, and reviewing the resulting real moments.

## Intent

Treat the app like it is about to be filmed for a skeptical audience. Build a resettable, product-faithful demo fixture; rehearse several plausible paths; and correct anything a viewer would notice as confusing, unfinished, generic, or visually weak. Only after the rehearsal is clean should the final recording runbook choose its narrative and shots.

## Work

- [ ] Create a resettable persisted demo fixture with a populated Studio, an employee owning two explicitly scoped tasks, an active or reviewable native Codex session, a visibly queued task under the one-writer rule, and actionable task-specific Inbox/decision states. All displayed activity and output must be real or plainly labelled as a saved historical record; do not present invented execution as live Codex work.
- [ ] Exercise the fixture as an audience rehearsal rather than following a prewritten trailer. Explore task workspace, Session terminal/history, task board, Inbox, decision/reply routing, queue state, and return-to-Studio paths. Record the candidate moments that are genuinely clear and compelling.
- [ ] Correct viewer-visible flaws found in that rehearsal: ambiguous ownership or queue state, empty/error/filler panels, stale or distracting fixture copy, weak task-card hierarchy, terminal framing/noise, awkward navigation, inconsistent room/sprite states, cropped narrow layouts, unreadable contrast, and motion that interferes with a shot. Preserve the approved pixel-office direction and product truth.
- [ ] Verify desktop and narrow layouts, keyboard navigation, and reduced-motion behavior for every surface likely to appear in the recording. Do not hide a broken state solely for the demo; either repair it, avoid claiming it works, or keep it out of the approved run.
- [ ] Repeat a full reset-and-rehearsal twice. The second pass must reproduce the same task/session identity, context, queue state, and Inbox routing without manual database surgery.
- [ ] After—not before—the clean rehearsals, write a concise recording runbook that selects the best observed moments, names any required real interaction, gives reset instructions, identifies disqualifying states, and distinguishes cuts/editing from live product behavior.

## Acceptance

A reviewer can reset the fixture and independently reproduce a clean desktop walkthrough twice. The walkthrough shows a populated Studio, task-first workspace, real native terminal/history for the selected task, two-task ownership with sequential queue state, and exact Inbox/decision routing. No visible shot contains placeholder/test language, a misleading live-execution claim, an unexplained empty/failure state, or a task-boundary leak. Narrow, keyboard, and reduced-motion checks pass. The final runbook is based on the observed rehearsal—not assumed in advance—and contains only product-faithful shots.

## Boundary and handoff

No second provider/account profile (4A), usage fallback (4B), concurrent execution/workspace isolation (5A), employee-to-employee delegation (5B), delivery expansion, or standalone video-editing pipeline. Do not use mock execution to manufacture a product claim. Leave the reset procedure, fixture provenance, rehearsal observations, visual fixes, acceptance screenshots, and final recording runbook for the next session.
