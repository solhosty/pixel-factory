# 2C — Coworker list, office task board, and machine capacity

Prerequisite: 2B.

## Work

- [ ] Make the all-coworker list the default coworker view across projects, including available and assigned staff. Keep the office as an explicit alternate view. Opening a coworker retains the existing conversation/actual-terminal flow and session identity.
- [ ] Add an office-wide task board across all projects, similar in purpose to research-harness. Show task, project, assigned coworker (or unassigned), status, execution location, and blocking reason. Provide project, coworker, and status filters; open the underlying task/session directly. Use the same persisted records as the coworker list and office, so assignment and status changes agree across views.
- [ ] Show each coworker's project/task, working state, and execution location. Provide All, In office, and Remote filters, with All selected by default.
- [ ] Local coworkers, including available staff, appear in the company Office. Remote coworkers are assigned to Coder environments and remain visible in the list without being placed physically in the Office or consuming a workstation. Persist their environment binding separately from identity and assignment history; show unavailable/disconnected locations honestly.
- [ ] Introduce a capacity policy per execution machine/environment based on usable CPU and memory, with headroom for the OS, app, and task subprocesses. Record the measurement source, freshness, per-worker resource estimate, and resulting limit. Establish and document conservative estimates using bounded measurements; do not claim CPU/RAM alone guarantees a workload will fit.
- [ ] Enforce admission in the service before launch, counting reserved and active sessions/processes rather than roster size. Account for multiple sessions under one employee and shared capacity where environments share a host. Preserve stricter existing sequential/account/project limits.
- [ ] Show active/reserved slots, effective limit, and a distinct waiting-for-capacity reason. Retain excess assignments without launching them. Allow a lower user ceiling; missing/stale resource data must not imply unlimited capacity. Define conservative fallback and recheck behavior without killing running work solely because a limit decreases.

## Acceptance

Verify the office-wide board with tasks across multiple projects, unassigned tasks, working/completed tasks, and approval/capacity blocks. Assignment and status changes must agree across board, list, and office after reload.

Open and reload the app into the all-coworker list. Exercise filters, available staff, multiple projects, and navigation into the same conversation/terminal session from list and office. Verify that only in-office coworkers appear in rooms and remote coworkers remain discoverable when disconnected. Until real Coder execution is implemented, remote acceptance uses explicitly labeled fixtures and does not claim a working remote connection.

Use deterministic capacity fixtures for CPU-limited, memory-limited, missing/stale data, shared-host accounting, and multiple sessions under one employee. Prove simultaneous launch requests cannot reserve beyond the effective limit, excess work remains pending, and exit/cancel releases a slot only after ownership reconciliation. Show a bounded real local launch passing the capacity gate. Keep actual execution sequential until 5A.

## Boundary and handoff

This packet changes coworker navigation and establishes capacity admission; parallel execution remains in 5A and working Coder onboarding/execution remains in 6 unless the user explicitly brings that integration forward. Saved staff count is not capped by execution capacity. Leave the capacity contract, measurement assumptions, fixture evidence, and integration points for 2D recovery, 5A scheduling, and 6 remote resource discovery. No artwork generation is required by this packet.
