# 3A — Decision meetings and approval versions

Prerequisite: 2D.

## Work

- [ ] Build UI option presentations with pictures/previews, feedback, revised versions, and explicit approval in the meeting interface.
- [ ] Implement project-level technical proposals with alternatives, tradeoffs, recommendation, feedback, and supersession.
- [ ] Link affected tasks and scope gates so independent authorized work can continue.
- [ ] Store approved decisions in project guidance and expose pending meetings through the inbox.
- [ ] Show which exact option/version was approved and reopen the gate for material changes.

## Acceptance

An employee presents UI options, revises after feedback, and starts implementation only after approval. A technical proposal is revised and approved; another task honors it. Reload and session continuation preserve pending gates. No timeout grants approval. Test stale-version approval rejection. Compare the full meeting flow with approved visual references.

## Boundary and handoff

This is the product's decision interface, distinct from this repository's 0A design approval record. Do not silently generate new product art during implementation. Cheaper models can implement approved meeting components and state transitions; material layout changes need concrete visual review.
