# 00 — Execution feasibility and contracts

Prerequisites: none. Read the product specification and decision register. This is engineering investigation, not full implementation.

## Work

- [ ] Inspect installed Codex capabilities and current official protocol documentation; record exact versions and sources. Use disposable folders and a bounded live task for the probe.
- [ ] Prove conversation events and a real interactive terminal can address the same execution. Exercise output, input ownership, terminal resizing, follow-up input, cancellation, and a second sequential session. Record process/session identifiers. Do not claim that headless output is the native terminal.
- [ ] Probe two selected folders, native authentication detection, interrupted recovery, and any unavailable permissions behavior. Avoid exposing credentials.
- [ ] If a required capability fails, supply a minimal reproduction and concrete alternatives for user review. Do not silently weaken the requirement or build downstream on an unsupported assumption.
- [ ] Record E01/E02. Propose the smallest coherent stack, supported browser, service/frontend boundary, persistence, renderer requirements, and install/build/test/run commands. Material architecture choices receive review before broad implementation.
- [ ] Write `docs/architecture/CONTRACTS.md` and `docs/architecture/VALIDATION.md` with actual selected file paths and commands. Include entity identifiers/relations, versioned events, API error shape, worker ownership, queued message semantics, approval versions, stop reasons, credential boundaries, migrations, and simulated worker fixtures. Employee identity must remain separate from session and attempt identity.
- [ ] Define localhost binding, request authentication/origin checks, allowed workspace selection, and terminal input routing. A website in another tab must not be able to dispatch local commands.

## Acceptance

Two views demonstrably control/observe one execution; a two-folder edit is verified; interruption and input limitations are recorded honestly. Exact reproducible probe commands and output references exist. The selected stack and contracts are recorded with approval where needed. If the two-view contract is unresolved, this packet stays blocked or needs review, not complete.

## Boundary and handoff

No artwork, full office, remote execution, or broad backend port. Leave the probe and contract files, verified runtime versions, known limitations, and next commands. Most reasoning belongs here: use a capable session for protocol/architecture decisions; cheaper execution sessions can implement isolated probes from an exact spec.
